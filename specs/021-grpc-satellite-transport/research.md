# Phase 0 Research: gRPC Satellite Transport

All Technical-Context unknowns resolved. Each item: **Decision / Rationale /
Alternatives considered**, grounded in the existing codebase where relevant.

---

## R-1 — gRPC stack: `grpcio` async server (`grpc.aio`)

**Decision**: Host `Audio.Stream` (and Phase-2 `Management`) on a
`grpc.aio.Server` started/stopped from `AivgSatelliteAdapter.start()/stop()`,
alongside the existing aiohttp sites. Add `grpcio` (runtime) + `grpcio-tools`
(build) + `protobuf` (runtime) to `pyproject.toml`.

**Rationale**: The gateway is already fully `asyncio` (aiohttp, the esphome
`asyncio.start_server`). `grpc.aio` integrates with the running loop and lets a
servicer `async for` over the request iterator and `yield` responses — a direct
match for `MediaTransport`. `grpcio` is a pure consumer-side dep on the
gateway host (Hermes venv), not on-device.

**Correction to the proposal**: The proposal states "already have `grpcio`
(aivg dep tree pulls it via protobuf)." Verified false — `aioesphomeapi` pulls
`protobuf` but **not** `grpcio`. Treat `grpcio` as a genuine new dependency.

**Alternatives**: (a) raw protobuf-over-TCP like the esphome transport — loses
HTTP/2 multiplexing, reflection, `grpcurl`, deadlines; defeats the rationale.
(b) `grpclib` (pure-Python) — lighter but less battle-tested and no first-class
reflection; `grpcio` is the reference impl and matches the C++ client's `grpc-cpp`.

## R-2 — Where the canonical `.proto` lives & codegen

**Decision**: Canonical schema at repo-root **`proto/aivg/satellite/v1/{audio,management}.proto`** (language-neutral, the single source of truth per FR-001). Python bindings are generated by `scripts/gen_proto.sh` (`python -m grpc_tools.protoc`) into `src/aivg_core/transports/grpc/_generated/` and **checked into git**. The `aivg-devices` C++ repo vendors `proto/` (copy or git-subtree) and runs its own codegen.

**Rationale**: Checked-in stubs mean `pip install aivg` needs no `protoc`
toolchain (matches how the esphome transport ships pre-generated `api_pb2`). A
single repo-root `proto/` tree is the natural shared origin for both languages
and keeps the contract un-droppable (FR-004). A `contract`-style test asserts
the checked-in stubs match the `.proto` (regen-and-diff) so they can't drift.

**Alternatives**: (a) generate at install/runtime — adds a `protoc` build
dependency to every install, rejected. (b) put `.proto` under
`src/aivg_core/transports/grpc/proto/` — works, but burying the cross-language
contract inside the Python package obscures that `aivg-devices` shares it;
repo-root `proto/` signals "shared contract."

## R-3 — Mapping the schema onto the `MediaTransport` seam

**Decision**: A per-stream `GrpcMediaAdapter` implements the existing
`MediaTransport` Protocol (`webrtc/session.py:67`):
`receive() / send_audio() / stop_playback() / connection_state / close()`. The
`stream_handler` constructs a `VoiceSession` model + `GrpcMediaAdapter` +
`Session(...)` and runs it — identical to how `esphome/connection.py:_start_voice_pipeline()` does it.

Frame mapping (`audio.proto`):
- Upstream `ClientFrame.pcm` → `GrpcMediaAdapter.push_inbound()` → `receive()`.
- Upstream `ClientFrame.event{END_OF_UTTERANCE}` → `push_eof()` (the EOF the
  `Session` loop expects, mirroring esphome `push_eof`).
- Upstream `ClientFrame.event{WAKE_FIRED}` → explicit session start (FR-012).
- Upstream `ClientFrame.event{BARGE_IN_START}` → `Session` barge-in path.
- Downstream `Session.send_audio(pcm)` → `GrpcMediaAdapter.drain_outbound()` →
  `codec.encode()` → `ServerFrame.audio`.
- `Session` UI events (`_ui()`: state/partial transcript) → `ServerFrame.event`
  / `ServerFrame.transcript` on the **same stream** (FR-010), instead of the
  WebRTC SCTP datachannel + control-WS fan-out.

**Rationale**: Reuses the proven, transport-agnostic `Session` state machine
(barge-in ≤300 ms, single-turn-in-flight, reconnect) with zero changes —
Constitution I/IV preserved. The esphome `media_adapter.py` is the working
reference for the queue + resample shape.

**Alternatives**: a bespoke gRPC-specific session loop — rejected; forks the
state machine and re-litigates barge-in/endpointing.

## R-4 — Audio formats & codec

**Decision**: **Upstream** PCM `s16le` mono **16 kHz**, 20 ms frames (640 B)
exactly as the proposal. **Downstream** codec is gateway-chosen and explicit in
`AudioChunk.codec`; default **Opus** when the client advertises it, else
`PCM_S16LE_16K`. The client's `SessionHeader.downstream_codec_pref` drives the
choice.

**Rationale**: 16 kHz `s16le` is what the STT path consumes; the existing
esphome adapter already resamples 16 kHz↔48 kHz internally, so the `Session`'s
internal 48 kHz expectation is bridged in `GrpcMediaAdapter` the same way
(`audioop.ratecv`). Opus downstream (~100 KB libopus on the Pi) cuts LAN
bandwidth and gives the client one downstream format. Explicit codec in the
frame avoids the "assume PCM" drift.

**Open implementation note (tasks, not a blocker)**: confirm the gateway TTS
output sample rate and whether an Opus encoder is already available in the
Hermes venv or must be added; PCM-only downstream is the safe fallback for the
Phase-1 MVP, Opus is an optimization that can land in Phase 1b.

**Alternatives**: PCM-only both directions — simplest, but wastes LAN bandwidth
and diverges from the proposal; kept as the fallback, not the default.

## R-5 — Transport capability negotiation & coexistence (US3)

**Decision**: Extend the existing adoption/registration flow so a satellite
advertises `transport_capabilities: ["grpc","webrtc"]`. The gateway selects the
best mutually-supported transport (prefer `grpc` for native, `webrtc` for
browser) and records the chosen `transport` on `ConnectedClient`/`VoiceSession`
(the field already exists, defaulting to `"webrtc"`, set to `"esphome_api"` by
that transport today — `models.py:220/262`). An operator override pins a
satellite's transport; an unsatisfiable pin surfaces a clear error.

**Rationale**: The `transport` discriminator and the per-transport edge-setting
pattern already exist; this generalizes "implicitly set by whichever transport
authenticated" into "explicitly negotiated from advertised capabilities,"
without the gateway core branching on `device_type`/transport (Constitution II).
Browser tabs simply never advertise `grpc`.

**Alternatives**: gateway-global "grpc on/off" with no per-device negotiation —
rejected; breaks mixed fleets and the no-flag-day requirement (FR-018).

## R-6 — Reconnect, backpressure, security (the three proposal open-questions)

**Decision**:
- **Reconnect (FR-019/020)**: a dropped `Audio.Stream` ends the session; the
  satellite surfaces it to the user (tone cue, client-side) and the **next**
  wake opens a fresh stream. No silent auto-retry of a dead voice call. After a
  gateway restart the satellite's next turn just dials a new stream — no peer
  renegotiation, which is the whole point (kills the watchdog/boot-order
  workarounds).
- **Backpressure (FR-021)**: rely on HTTP/2 flow control; `GrpcMediaAdapter`'s
  outbound queue is **bounded** and drops/blocks deterministically so a slow Pi
  cannot make the gateway buffer unboundedly. Surface `RESOURCE_EXHAUSTED`
  cleanly on both ends.
- **Security (FR-022)**: trusted-LAN default = `insecure` server credentials
  (matches Alexa's "trust the LAN," and Constitution Hardware note "Security…
  deferred… revisit before any non-LAN deployment"). Fleet = mTLS via
  `grpc.ssl_server_credentials`, reusing the device-keystore pattern
  (`KeystoreResolver`) the esphome transport already uses. Never silently
  downgrade from a required-auth posture.

**Rationale**: These directly answer the proposal's Open Questions with the
least machinery; each is a first-class gRPC primitive rather than hand-rolled.

**Alternatives**: app-level retry of the audio call — rejected; "retry a voice
turn" is semantically "start a new turn," and silent reconnect hides failures
the user should hear.

## R-7 — Constitution Principle III reconciliation

**Decision**: Phase 1 keeps the always-on `/satellite/ws` **control WebSocket**
intact and swaps **only** the per-session voice transport WebRTC→gRPC. Phase 2
moves control to a **separate** long-lived gRPC `Management` service, kept
distinct from the per-session `Audio.Stream` (durable control is never
multiplexed into the audio stream). Recommend a follow-up constitution
amendment generalizing III's wording from "WebRTC voice connection" / "WS
control" to transport-neutral "a per-session voice connection" / "an always-on
control connection," mirroring the v2.0.0 generalization of IV.

**Rationale**: III's binding *intent* — control availability decoupled from
call state, durable traffic off the call-scoped channel, exactly two
connections — is fully honored under gRPC. Only the named technologies change.
Recording the deviation now (plan Complexity Tracking) satisfies the
governance rule that any departure be justified against its binding constraint;
the amendment is a separate governance action, not a code blocker.

**Alternatives**: amend the constitution *before* coding — cleaner governance,
but the amendment is broader than this feature and shouldn't gate Phase 1; the
recorded-deviation path is the established precedent (feature 020's Principle V
`libpeer`/`esp_peer` deviation).

## R-8 — Contract-version envelope & `SUPPORTED_TRANSPORTS`

**Decision**: When the gRPC transport ships and can be advertised, add `"grpc"`
to `SUPPORTED_TRANSPORTS` (`cli.py`) and bump the `contract_version` envelope
**0.2.0 → 0.3.0** (additive minor, same shape as feature 017's `1.0.0→1.1.0`
ESPHome additive bump). Until opt-in, the envelope is unchanged.

**Rationale**: Adding a transport is additive and backward-compatible; existing
WebRTC/esphome clients are unaffected. Minor bump signals new capability
without implying a breaking wire change.

**Alternatives**: no bump — rejected; the advertised transport set is part of
the observable contract and should version when it grows.
