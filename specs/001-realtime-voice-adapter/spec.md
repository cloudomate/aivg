# Feature Specification: Realtime Voice Platform Adapter

**Feature Branch**: `001-realtime-voice-adapter`
**Created**: 2026-05-18
**Status**: Draft
**Input**: User description: "build the platform adapter for hermes gateway for stt and tts for realtime conversation using hermes managed tts and stt services and hermes agent is involed as an entity"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Hold a real-time spoken conversation through the gateway (Priority: P1)

A person speaks to a connected voice client. Their speech is carried to the
Hermes gateway, transcribed by Hermes's managed speech-to-text service, handled
by the Hermes agent as a conversational entity, spoken back through Hermes's
managed text-to-speech service, and played to the person — fast enough to feel
like a live conversation, not a walkie-talkie.

**Why this priority**: This is the entire purpose of the feature. Without a
working speech-in → agent → speech-out loop there is no product. It is the
minimum viable slice and every other story builds on it.

**Independent Test**: Connect a single voice client, speak a short request,
and confirm an agent-generated spoken reply is heard. Delivers value on its
own (a usable voice assistant) with no other story implemented.

**Acceptance Scenarios**:

1. **Given** a voice client is connected to the gateway, **When** the person
   finishes speaking an utterance, **Then** a spoken reply generated by the
   Hermes agent begins playing back within a conversational delay.
2. **Given** Hermes is configured with a specific speech-to-text and
   text-to-speech provider, **When** a conversation occurs through the adapter,
   **Then** the conversation uses exactly those configured providers (and their
   configured fallbacks) with no separate provider configuration.
3. **Given** the person stops speaking, **When** the gateway's existing
   end-of-utterance detection determines the turn is complete, **Then** the
   agent turn is triggered using that determination (not a device-local guess).
4. **Given** the Hermes agent produces a multi-sentence reply, **When** it is
   spoken back, **Then** the audio is a continuous natural utterance without
   gaps that break comprehension.

---

### User Story 2 - Interrupt the agent mid-reply (barge-in) (Priority: P2)

While the agent is speaking, the person starts talking over it. The agent
stops speaking promptly and listens to the new input, the way a human
conversation partner would.

**Why this priority**: Real-time conversation feels broken if the user cannot
interrupt. High value, but the basic loop (P1) is usable without it for short
exchanges, so it is P2.

**Independent Test**: During agent playback, speak over the agent and confirm
playback stops quickly and the new utterance is captured and answered.

**Acceptance Scenarios**:

1. **Given** the agent is speaking a reply, **When** the person begins
   speaking, **Then** agent playback stops promptly and the new utterance is
   processed as the next turn.
2. **Given** an interruption occurred, **When** the agent responds again,
   **Then** the response addresses the interrupting utterance, not the
   abandoned one.

---

### User Story 3 - Operator monitors active voice sessions (Priority: P2)

An operator running the Hermes gateway can see which voice clients are
connected, the live state of each conversation (idle / listening / thinking /
speaking), and per-session diagnostic logs, using the gateway's existing
operational surfaces.

**Why this priority**: Operators must be able to confirm the feature is alive
and triage failures. Not required for an end user to converse, so P2.

**Independent Test**: With one or more clients connected, query the gateway
and confirm each session is listed with its current state and that per-session
logs are retrievable.

**Acceptance Scenarios**:

1. **Given** voice clients are connected, **When** the operator inspects the
   gateway, **Then** each connected client and its current conversation state
   is listed.
2. **Given** a conversation produced an error, **When** the operator views
   logs, **Then** the error is recorded in the gateway's existing log stream
   attributable to the specific session.

---

### User Story 4 - Survive a dropped connection (Priority: P3)

A voice client temporarily loses its network connection. When connectivity
returns, the client is recognized again and conversation can resume without an
operator manually intervening.

**Why this priority**: Improves robustness for real deployments but the core
conversation works without it, so P3.

**Independent Test**: Drop a connected client's network mid-session, restore
it, and confirm the client is usable again without operator action.

**Acceptance Scenarios**:

1. **Given** a connected client loses its network, **When** connectivity
   returns, **Then** the client re-establishes its session automatically and
   appears connected again.
2. **Given** a voice stream drops mid-conversation, **When** the client
   reconnects, **Then** a new conversation can be started without restarting
   the gateway.

### Edge Cases

- What happens when the configured speech-to-text or text-to-speech provider
  is unavailable? The conversation falls back per Hermes's existing provider
  fallback order; if all fail, the user is informed gracefully rather than
  left in silence.
- How does the system handle a person who never stops talking (no natural
  pause)? The gateway's existing end-of-utterance logic governs turn end;
  there must be no infinite "listening" state with no turn ever taken.
- What happens when two utterances arrive almost simultaneously on one
  session? Only one agent turn is in flight per session at a time; the later
  input is treated as a barge-in or queued, never producing two overlapping
  spoken replies.
- What happens when a client connects but never sends audio? The session is
  tracked as connected/idle and consumes no transcription or agent work until
  speech arrives.
- What happens if the agent produces no reply (empty or tool-only turn)? The
  session returns cleanly to listening without emitting broken audio.
- What happens when the gateway is restarted while a call is active? Active
  voice sessions end; clients re-register and resume per User Story 4 without
  manual cleanup.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The system MUST accept a real-time inbound voice stream from a
  connected voice client and produce a real-time outbound voice stream back to
  that same client within a single conversational session.
- **FR-002**: The system MUST transcribe inbound speech using Hermes's
  managed speech-to-text service and MUST NOT perform or embed its own speech
  recognition.
- **FR-003**: The system MUST synthesize the agent's spoken reply using
  Hermes's managed text-to-speech service and MUST NOT perform or embed its
  own speech synthesis.
- **FR-004**: The system MUST invoke the Hermes agent as the conversational
  entity for each completed user turn, using the same agent invocation path
  used by other Hermes platform adapters.
- **FR-005**: The system MUST use Hermes's existing authoritative
  end-of-utterance / silence detection to decide when a user turn is complete;
  any client-side voice activity signal MAY only gate what is streamed
  upstream and MUST NOT override the gateway's turn-end decision.
- **FR-006**: The system MUST inherit Hermes's configured speech-to-text and
  text-to-speech provider selection and fallback order, with no separate
  provider configuration of its own.
- **FR-007**: The system MUST register and operate as a platform adapter
  within the existing Hermes gateway (analogous to existing adapters), not as
  a separate standalone service or pipeline.
- **FR-008**: The system MUST maintain a control channel for each client that
  remains available when no conversation is active (for presence, lifecycle,
  and configuration), separate from the per-conversation voice channel.
- **FR-009**: The system MUST track each connected client and expose, through
  the gateway's existing operational surfaces, the client list and each
  session's current conversation state.
- **FR-010**: The system MUST record per-session diagnostic events into
  Hermes's existing log stream, attributable to the originating session.
- **FR-011**: The system MUST support barge-in: when a user speaks during
  agent playback, agent playback MUST stop promptly and the new utterance MUST
  become the next turn.
- **FR-012**: The system MUST process at most one agent turn at a time per
  session and MUST NOT emit overlapping spoken replies for one session.
- **FR-013**: The system MUST take its configuration from Hermes's existing
  gateway configuration mechanism and MUST NOT introduce a separate
  configuration or secret store.
- **FR-014**: The system MUST recover from a dropped client connection by
  allowing the client to re-establish its session automatically without
  operator intervention or a gateway restart.
- **FR-015**: When all configured speech providers are unavailable, the system
  MUST fail gracefully with a perceptible indication rather than silent or
  hung sessions.

### Key Entities *(include if feature involves data)*

- **Voice Session**: A single client's live conversation context with the
  gateway. Attributes: associated client identity, current state (idle /
  listening / thinking / speaking / error), start time, last activity, last
  error. One active agent turn at a time.
- **Connected Client**: A registered voice endpoint known to the gateway.
  Attributes: client identity, presence status (online / offline /
  connecting), last seen, current associated voice session (if any).
- **Conversation Turn**: One user-utterance → agent-reply exchange within a
  session. Attributes: transcribed user input, agent reply text, outcome
  (completed / interrupted / failed).
- **Hermes Agent**: The existing conversational entity that consumes a
  completed user turn and produces a reply; reused, not defined by this
  feature.
- **Speech Services**: Hermes's existing managed speech-to-text and
  text-to-speech capabilities, including their configured provider selection
  and fallback order; consumed, not defined by this feature.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: For a typical short utterance, the spoken agent reply begins
  playing within 1.5 seconds of the user finishing speaking, under nominal
  network and provider conditions.
- **SC-002**: At least 95% of completed utterances in a normal conversation
  produce a corresponding spoken agent reply (no dropped turns).
- **SC-003**: When a user interrupts the agent, agent playback stops within
  300 milliseconds of detected user speech.
- **SC-004**: Transcription accuracy and voice quality experienced through the
  adapter are equivalent to using the same configured Hermes speech providers
  directly (the adapter introduces no measurable quality regression).
- **SC-005**: The gateway sustains at least 10 concurrent voice sessions
  without any session exceeding the SC-001 latency target by more than 50%.
- **SC-006**: The per-client control channel remains available at least 99% of
  the time the gateway is running, including during periods with no active
  conversation.
- **SC-007**: After a client network drop, the client returns to a usable
  state within 30 seconds of connectivity being restored, with no operator
  action.
- **SC-008**: An operator can identify any connected client and its current
  conversation state within 5 seconds using existing gateway surfaces.

## Assumptions

- This feature covers the **gateway-side platform adapter only**. The
  device/satellite client implementations (Raspberry Pi, ESP32, browser) are
  out of scope here and specified separately; this adapter must serve all of
  them through one device-agnostic contract.
- Hermes already provides managed speech-to-text and text-to-speech services
  with provider selection and fallback, an agent invocation path used by
  existing platform adapters, an authoritative server-side end-of-utterance /
  silence detection algorithm, a gateway configuration mechanism, and a shared
  log stream. These are reused unchanged, per the project constitution.
- "Real-time conversation" means full-duplex-capable interactive turn-taking
  with barge-in, not a record-then-playback exchange.
- Conversational latency target (SC-001) reflects standard expectations for a
  responsive voice assistant; the adapter's own added latency is expected to
  be a small fraction of the total, with most latency owned by the speech
  providers and agent.
- Transport security and per-client authentication are deferred for the
  current LAN-oriented scope (consistent with the design's deferred-security
  note) and must be revisited before any non-LAN deployment; they are out of
  scope for this specification.
- A single Hermes agent entity handles a session's turns; multi-agent routing
  is out of scope.
- Initial concurrency expectations are modest (small fleet on a LAN);
  large-scale horizontal scaling is out of scope for this version.
