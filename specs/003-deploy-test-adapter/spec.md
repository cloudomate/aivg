# Feature Specification: Deploy & Live-Test the Voice Adapter on the Hermes Gateway

**Feature Branch**: `003-deploy-test-adapter`
**Created**: 2026-05-18
**Status**: Draft
**Input**: User description: "i want to deploy the gateway adapter to hermes gateway and test actual implementation i am ok with electron/js app for testing"

## Overview

Features `001` (the realtime voice platform adapter) and its v0.13.0 wiring are
implemented and verified against the real Hermes API, but have never run a real
conversation against the live gateway — feature 001's T045 is still open
specifically because that needs a real WebRTC client. This feature **deploys
the adapter onto the running Hermes gateway and validates the actual
implementation end-to-end using an Electron/JS desktop test client** (the
design's satellite #3). It closes the live-validation gap with a real
speech-in → agent → speech-out loop, and does so **safely and reversibly** —
deployment touches a production gateway, so backup, confirmation, and rollback
are first-class requirements, consistent with this project's established
outward-action posture and constitution Principle V (verify before relying).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Deploy the adapter onto the Hermes gateway without breaking it (Priority: P1)

An operator deploys the voice adapter to the running Hermes gateway: the
adapter is registered as a platform, its `satellite:` configuration is added,
and the gateway serves the adapter's management and WebRTC endpoints — while
all pre-existing gateway functionality (other platforms, agent, STT/TTS) keeps
working.

**Why this priority**: Nothing can be tested until the adapter is actually
running on the gateway. This is the foundational step and the first place
production risk appears.

**Independent Test**: After deployment, the adapter appears as a registered
platform and its endpoints respond, while a pre-existing gateway capability
still works unchanged.

**Acceptance Scenarios**:

1. **Given** the Hermes gateway is running, **When** the adapter is deployed,
   **Then** it is registered/enabled and its management and WebRTC endpoints
   are reachable.
2. **Given** the adapter is deployed, **When** the gateway's existing
   functions are exercised, **Then** they behave exactly as before deployment.
3. **Given** any step would change the gateway host or its configuration,
   **When** that step is reached, **Then** it is presented for explicit
   confirmation before taking effect.

---

### User Story 2 - Hold a real spoken conversation from the Electron test client (Priority: P1)

A person runs the Electron/JS test app, connects to the deployed adapter,
speaks a request, and hears the Hermes agent's spoken reply — a genuine
end-to-end conversation through the real gateway, real STT, real agent, real
TTS.

**Why this priority**: This is the actual ask — "test actual implementation."
It is the definitive validation that the whole stack works against the live
build, not a fake.

**Independent Test**: From the Electron app, complete one spoken exchange and
hear an agent-generated reply produced by the real Hermes providers.

**Acceptance Scenarios**:

1. **Given** the adapter is deployed and the Electron app is connected,
   **When** the person speaks an utterance and finishes, **Then** a spoken
   reply generated by the real Hermes agent is heard within a conversational
   delay.
2. **Given** a conversation occurs, **When** transcription and synthesis run,
   **Then** they use the gateway's actually-configured STT/TTS providers
   (parity with calling those providers directly).
3. **Given** the person speaks while the agent is replying, **When** barge-in
   occurs, **Then** playback stops promptly and the new utterance is handled.
4. **Given** the Electron app is on the same device as its speaker/mic,
   **When** the agent's audio plays, **Then** it does not echo back as new
   input (local echo handled on the client side).

---

### User Story 3 - Deploy reversibly with a one-step rollback (Priority: P2)

Before any change to the gateway, the prior state is backed up; after testing
(or on failure) the operator can restore the gateway to exactly its
pre-deployment state with a single, reliable action.

**Why this priority**: Deploying onto a production gateway is only acceptable
if it is cleanly undoable. High value, but US1/US2 define what is being made
reversible, so P2.

**Independent Test**: Capture pre-state, deploy, then roll back, and confirm
the gateway is byte-for-byte back to its pre-deployment configuration and
behaviour.

**Acceptance Scenarios**:

1. **Given** a deployment is about to start, **When** it begins, **Then** the
   gateway's prior configuration/state is backed up first.
2. **Given** the adapter is deployed, **When** rollback is invoked, **Then**
   the adapter is removed/disabled and the gateway configuration is restored to
   the backed-up state.
3. **Given** deployment fails midway, **When** the failure is detected,
   **Then** the gateway is left either in its prior working state or clearly
   flagged as needing rollback — never silently half-deployed.

---

### User Story 4 - Observe and validate the live session (Priority: P2)

While testing, the operator can see the connected client, the live session
state, and per-session logs, and can get a clear pass/fail for the end-to-end
test using the deployed management surface and Hermes's own health checks.

**Why this priority**: Confirms the test actually exercised the real path and
gives an auditable result; not required to have a conversation, so P2.

**Independent Test**: During a test conversation, the operator can list the
connected client, see its state transitions, retrieve logs, and obtain a
recorded pass/fail.

**Acceptance Scenarios**:

1. **Given** the Electron client is connected, **When** the operator inspects
   the gateway, **Then** the client and its live conversation state are
   visible.
2. **Given** a test conversation completed, **When** results are reviewed,
   **Then** a clear pass/fail with the measured response latency is recorded.

---

### User Story 5 - Redeploy after code changes without manual cleanup (Priority: P3)

After changing adapter code, the operator can redeploy and re-test repeatably
without hand-cleaning the previous deployment.

**Why this priority**: Speeds iteration during validation, but a single
deploy/test cycle delivers the core value, so P3.

**Independent Test**: Deploy, change adapter code, redeploy, and confirm the
new version is what runs with no leftover state from the prior deploy.

**Acceptance Scenarios**:

1. **Given** a prior deployment exists, **When** the operator redeploys a new
   adapter version, **Then** the running adapter is the new version and no
   stale prior-version state remains.

### Edge Cases

- The Hermes gateway is not running / unreachable when deployment starts → the
  deployment aborts before any change and reports it; nothing is half-applied.
- The Electron client cannot reach the adapter's endpoints (network/port
  path) → the failure is reported with the connectivity cause, not a silent
  hang.
- A configured STT/TTS provider is unavailable during the live test → behaviour
  follows the gateway's existing provider fallback; if all fail the user gets a
  perceptible failure, and the test is recorded as failed (not falsely passed).
- Deployment partially applied then interrupted → state is recoverable to
  pre-deployment via the backup; the operator is told rollback is needed.
- The agent reply is empty/tool-only → the session returns cleanly to
  listening; the test harness does not hang waiting for audio.
- Mic permission denied in the Electron app → the app surfaces the OS
  permission path; the test cannot be falsely marked passed without audio in.
- Pre-existing gateway platforms must keep working — any regression to them
  counts as a deployment failure even if the adapter itself works.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The system MUST deploy the voice adapter onto the running Hermes
  gateway such that it is registered/enabled and its management and WebRTC
  endpoints are reachable.
- **FR-002**: Deployment MUST NOT degrade or alter any pre-existing gateway
  capability (other platforms, agent, STT/TTS, existing config).
- **FR-003**: The system MUST back up the gateway's prior configuration/state
  before applying any change.
- **FR-004**: The system MUST require explicit confirmation before each action
  that mutates the gateway host or its configuration; read-only steps may
  proceed without confirmation.
- **FR-005**: The system MUST provide a single, reliable rollback that removes/
  disables the adapter and restores the backed-up gateway state.
- **FR-006**: If deployment fails midway, the system MUST leave the gateway in
  its prior working state or explicitly flag that rollback is required — never
  a silent partial deployment.
- **FR-007**: The system MUST provide an Electron/JS desktop test client that
  connects to the deployed adapter, captures microphone speech, plays back the
  returned audio, and handles its own local echo so playback is not re-captured.
- **FR-008**: The test client MUST let a person complete a full spoken exchange
  (speak → hear the agent's spoken reply) against the live gateway.
- **FR-009**: The end-to-end path MUST use the gateway's actually-configured
  STT/TTS providers and the real Hermes agent (no test doubles in the deployed
  path).
- **FR-010**: The system MUST support barge-in during the live test (speaking
  over the agent stops playback and starts a new turn).
- **FR-011**: The system MUST expose, via the deployed management surface, the
  connected client, its live session state, and per-session logs during the
  test.
- **FR-012**: The system MUST record a clear pass/fail result for the
  end-to-end test, including the measured time from end-of-speech to start of
  spoken reply.
- **FR-013**: The system MUST support repeatable redeploy of a new adapter
  version without manual cleanup of the prior deployment.
- **FR-014**: The deployed adapter MUST preserve the constitution's runtime
  guarantees — no embedded STT/TTS/agent/endpointing on the device side, agent
  remains gateway-owned, control and voice remain separate connections.

### Key Entities *(include if feature involves data)*

- **Deployment**: An applied installation of the adapter on the gateway —
  what was changed, when, and the backup reference enabling rollback.
- **Gateway State Backup**: The captured pre-deployment gateway configuration/
  state that rollback restores.
- **Electron Test Client**: The desktop app acting as the satellite — captures
  mic, plays reply audio, handles local echo, drives one conversation.
- **Live Test Session**: One end-to-end conversation instance under test — its
  state timeline, per-session logs, and pass/fail + latency result.
- **Test Result**: The recorded outcome (pass/fail, measured latency, notes)
  for an end-to-end run.
- **Hermes Gateway / Providers / Agent**: The real, deployed-against systems
  (reused, not defined here).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A person completes at least one full spoken conversation (speak →
  hear agent reply) through the deployed adapter from the Electron client.
- **SC-002**: The spoken agent reply begins within 1.5 seconds of the person
  finishing speaking, under nominal network/provider conditions.
- **SC-003**: Barge-in stops agent playback within 300 milliseconds of detected
  user speech during the live test.
- **SC-004**: Transcription/voice quality through the deployed adapter matches
  using the gateway's configured providers directly (no measurable regression).
- **SC-005**: 0 regressions to pre-existing gateway capabilities introduced by
  the deployment (verified before and after).
- **SC-006**: Rollback restores the gateway to its exact pre-deployment
  configuration in 100% of attempts, in under 5 minutes.
- **SC-007**: 100% of gateway-host-mutating actions are explicitly confirmed
  before taking effect; 0 silent partial deployments.
- **SC-008**: The operator can obtain the connected client, its live state, and
  a recorded pass/fail with latency within 1 minute of a test run.

## Assumptions

- The deployment target is the existing `ssh hermes` host (hermes-agent
  v0.13.0); the adapter registers via the verified platform-registry path
  (feature 001 T044) and reads a `satellite:` block from the existing
  `~/.hermes/config.yaml` (no new config/secret store).
- The Electron/JS test client runs on the developer's local machine and
  reaches the deployed adapter's management/WebRTC ports over the existing
  trusted network path (e.g. SSH port-forwarding); LAN-style reachability is
  assumed and exact port routing is a deployment detail, not a scope question.
- The Electron client implements the design's satellite #3: full ICE
  gather → offer, always-on control connection, hidden audio playback, and
  **push-to-talk for v1** (no wake word in v1); browser/Chromium echo
  cancellation handles local echo (`browser_aec3`).
- Transport security / per-client auth remain deferred for this LAN-scoped
  validation (consistent with feature 001); out of scope here.
- Host-mutating deployment steps require explicit confirmation and a prior
  backup, consistent with this project's outward-action posture and
  constitution Principle V; rollback is mandatory and tested.
- This feature consumes features 001 (adapter) and 002 (the vendored
  `hermes-agent` skill MAY be used to perform/validate gateway configuration);
  it does not re-implement the adapter or the Hermes intelligence.
- A single test client / single concurrent conversation is sufficient to
  validate the implementation; multi-client load is out of scope here
  (covered by feature 001's concurrency tests against the fake).
- "Test actual implementation" means a real human-driven spoken exchange
  through real Hermes providers — not an automated/synthetic audio harness.
